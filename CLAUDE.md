# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Angular frontend for **Bike Maintainer**, an app for tracking maintenance schedules
(by mileage and/or time) for motorcycles and cars, and logging completed maintenance.
This repo is frontend-only. Backend and API spec live in sibling repos:

- `../bike-maintainer-backend` — Spring Boot service, REST API under `/api/v1/...`.
- `../bike-maintainer-api` — OpenAPI spec for the REST interface.

The dev server proxies `/api` to `http://localhost:8090` (see `proxy.conf.json`) — start
the backend there before running `npm start`, or requests will 404 against the Angular
dev server itself instead of reaching the backend.

## Commands

```bash
npm install            # install deps
npm run generate:api   # regenerate src/app/api-client from ../bike-maintainer-api's OpenAPI spec
npm start              # dev server at http://localhost:4200 (proxies /api to :8090)
npm run build          # production build to dist/
npm run watch          # dev build in watch mode
npm test               # unit tests (Vitest via @angular/build:unit-test)
```

Single test / filtering:

```bash
npx ng test --include src/app/pages/vehicles/vehicles.spec.ts   # one file
npx ng test --filter "some test name"                            # by test name regex
npx ng test --watch=false                                        # single run, no watch
```

There is no linter configured (no ESLint config in the repo). Use `npx tsc -p tsconfig.app.json --noEmit`
to type-check and `npx ng build` to catch Angular template compile errors — `tsc` alone does not
validate templates.

## API client (generated, do not hand-edit)

`src/app/api-client/` is generated by `npm run generate:api` (OpenAPI Generator, `typescript-angular`)
from `../bike-maintainer-api`'s spec and is gitignored — it does not exist right after a fresh clone
and must be regenerated. It provides one injectable service per resource tag (`VehiclesService`,
`MaintenanceTasksService`, `MaintenanceLogsService`) plus typed request/response models, wired up via
`provideApi('')` in `app.config.ts` (empty base path so calls are relative, e.g. `/api/v1/vehicles`,
and go through the dev proxy / a reverse proxy in production). Never edit files under `api-client/`
directly — re-run the generator instead; if the backend spec changes, regenerate before trusting
service signatures or model shapes.

## Architecture

- **Standalone components only**, no NgModules. Every component uses
  `changeDetection: ChangeDetectionStrategy.OnPush`.
- **State is signals-first.** Local component state is plain `signal()`/`computed()`, not RxJS
  Subjects/BehaviorSubjects and not a store library. Server data is fetched with `rxResource` (from
  `@angular/core/rxjs-interop`), not manual `subscribe()` in `ngOnInit`. See
  `pages/vehicle-detail/vehicle-detail.ts` for the pattern: `rxResource({ params, stream })`, read
  via `.value()`/`.isLoading()`/`.error()`, refresh via `.reload()` after a mutation.
- **Routes are lazy-loaded** via `loadComponent` in `app.routes.ts`; there is one component per page
  under `src/app/pages/`.
- **Forms are template-driven by default**: `FormsModule` + `[ngModel]`/`(ngModelChange)` bound to
  signals (see the "Wartung erfassen" / "Wartungsaufgaben" tabs in `vehicle-detail.html`). The vehicle
  create/edit dialog (`shared/vehicle-form-dialog/`) is the one exception and uses
  `ReactiveFormsModule`/`FormBuilder` because of its validation requirements — follow whichever
  pattern the file you're editing already uses rather than mixing both in one component.
- **Styling is a hand-built design system, not Material's default look.** Angular Material modules
  are used for structural/behavioral components (`mat-card`, `mat-tab-group`, `mat-dialog`,
  `mat-icon`, `mat-spinner`), but form inputs and buttons intentionally do **not** use
  `mat-form-field`/`mat-input`/Material buttons — they use the hand-styled global classes
  (`.field`, `.field__label`, `.field__input`, `.btn`, `.btn--primary`, `.btn--ghost`, `.field__error`)
  defined once in `src/styles/_forms.scss` and included app-wide via `@use` in `src/styles.scss`.
  Reuse those classes for any new form; don't reintroduce `mat-form-field` for app forms.
- Colors/spacing use the CSS custom properties defined in `src/styles.scss` (`--bm-*`, `--status-*`)
  rather than hardcoded hex values, to stay consistent with the dark "Werkstatt" theme.
- **Gotcha:** `mat-card` sets `display: flex; flex-direction: column` on itself at the same CSS
  specificity as a component's own `.some-card { display: flex; ... }` override, and can win by
  source order — silently collapsing an intended row layout into a column. Don't fight this with
  `!important`; add an inner wrapper div inside the card and put the row layout on that instead.
- The app is German-only (`LOCALE_ID` is set to `de-DE` in `app.config.ts`, all UI copy is German) —
  don't add i18n scaffolding or English strings.
- Domain-specific formatting/computation helpers live next to the page that uses them rather than in
  a shared utils folder, e.g. `pages/vehicle-detail/maintenance-status.ts` (due/overdue status logic),
  `task-icon.ts` (icon-by-task-name heuristic), `task-interval.ts` (interval description text).
